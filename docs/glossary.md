# 📖 Business Analysis Glossary

> Quick-reference for the vocabulary you'll use every day. Add your own examples as you learn.

| Term | Plain-English meaning |
|------|----------------------|
| **Business Analyst (BA)** | The bridge between business needs and a technical/solution team. |
| **Requirement** | A documented need — what must be true for a solution to succeed. |
| **Business requirement** | The high-level *why*/goal (e.g., cut costs, speed up a process). |
| **Stakeholder requirement** | What a specific group of people needs. |
| **Functional requirement** | What the system must *do* (a behavior). |
| **Non-functional requirement (NFR)** | A *quality* of the system (speed, security, usability). |
| **Transition requirement** | Temporary need to move from old to new (migration, training). |
| **Stakeholder** | Anyone affected by or influencing the project. |
| **Elicitation** | The act of drawing out requirements from people/systems. |
| **BRD** | Business Requirements Document — the *why/what* at business level. |
| **FRD / SRS** | Functional Requirements Doc / Software Requirements Spec — detailed system behavior. |
| **User story** | Agile requirement: "As a &lt;role&gt;, I want &lt;goal&gt;, so that &lt;benefit&gt;." |
| **Acceptance criteria** | Conditions that make a story "done" and testable. |
| **Gherkin** | Given / When / Then format for acceptance criteria. |
| **Epic** | A large body of work split into many user stories. |
| **Backlog** | Prioritized list of everything the team might build. |
| **INVEST** | Qualities of a good story: Independent, Negotiable, Valuable, Estimable, Small, Testable. |
| **MoSCoW** | Prioritization: Must / Should / Could / Won't. |
| **BABOK** | Business Analysis Body of Knowledge — the IIBA standard guide. |
| **IIBA** | International Institute of Business Analysis (issues ECBA/CCBA/CBAP). |
| **BPMN** | Business Process Model & Notation — standard for process diagrams. |
| **UML** | Unified Modeling Language — diagrams like use case & activity. |
| **Use case** | A description of how an actor interacts with a system to reach a goal. |
| **As-Is / To-Be** | Current process vs. improved future process. |
| **Gap analysis** | Comparing current state to desired state; the gap = the work. |
| **SDLC** | Software Development Life Cycle. |
| **Agile** | Iterative, incremental delivery approach. |
| **Waterfall** | Sequential, phase-by-phase approach with upfront requirements. |
| **Scrum** | A popular Agile framework (sprints, roles, ceremonies). |
| **Sprint** | A short, fixed time-box (often 1–2 weeks) of work. |
| **Product Owner (PO)** | Owns and prioritizes the backlog; represents the business. |
| **Scrum Master** | Facilitates the Scrum process; removes blockers. |
| **RACI** | Responsible, Accountable, Consulted, Informed — a roles matrix. |
| **RTM** | Requirements Traceability Matrix — links goals → requirements → tests. |
| **ERD** | Entity Relationship Diagram — a data model. |
| **SQL** | Structured Query Language — for reading/analyzing data. |
| **Wireframe** | A low-detail sketch of a screen layout. |
| **Prototype** | A clickable/interactive mockup of a solution. |
| **Scope** | The boundary of what's included (and excluded) in a project. |
| **Jira** | Tool for managing backlogs, sprints, and tasks. |
| **Confluence** | Tool for documentation and collaboration. |
| **ERP** | Enterprise Resource Planning software (e.g., MISA) — integrates business processes. |
