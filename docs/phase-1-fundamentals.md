# 📘 Phase 1 — Core Fundamentals (The 80/20)

> **Goal:** Learn to *think* like a Business Analyst. This is the 20% of knowledge you'll use 80% of the time.
> **Est. time:** ~2 weeks · **Style:** mostly concept + small exercises.

---

## 🎯 Learning objectives

By the end of Phase 1 you will be able to:
- Separate a **problem/need** from a **solution** (the core BA reflex).
- Explain what a BA does across the software lifecycle.
- Identify the **four types of requirements**.
- Choose an appropriate **elicitation technique** for a situation.
- Do a basic **stakeholder analysis**.
- Recognize the core BA documents (**BRD, FRD/SRS, User Story**).
- Explain the BA's role in **Agile vs. Waterfall**.

---

## 📚 Lessons

### Lesson 1 — The BA Mindset: Problem vs. Solution ⭐
- **What:** BAs work in the *why* (need) and *what* (requirement) layers, not the *how* (solution) layer.
- **Why it matters:** Jumping to a solution too early is the #1 cause of failed software projects.
- **Analogy (your world):** A customer asks for an "Export to Excel button." Ask *why* → discover they really need an **automated monthly report**. The button may not even be the best answer.
- **Practice:** For any request you hear this week, write the hidden "why" behind it.

### Lesson 2 — What a BA Does Across the Lifecycle (SDLC)
- **What:** The Software Development Life Cycle (Plan → Analyze → Design → Build → Test → Deploy → Maintain) and where the BA is active (heavily in Analyze; supporting everywhere).
- **BA role types:** IT BA, Business/Process Analyst, Systems Analyst, Product Owner-adjacent, Data Analyst-adjacent.
- **Practice:** Map your old MISA implementation work onto SDLC stages — you'll see you already did BA-type work.

### Lesson 3 — The Four Types of Requirements
- **Business requirements** — the *why* (goals): "reduce month-end close from 5 days to 2."
- **Stakeholder requirements** — what a specific group needs: "accountants need to spot unmatched transactions."
- **Solution requirements** — the *what* to build, split into:
  - **Functional** (what the system does): "system shall flag transactions with no match."
  - **Non-functional** (qualities): performance, security, usability: "screen loads in < 2s."
- **Transition requirements** — temporary needs to go live: data migration, training.
- **Practice:** Write one example of each type for a fictional "invoice approval" feature.

### Lesson 4 — Requirements Elicitation Techniques
- **What:** Ways to *pull out* requirements from people & systems.
- **Key techniques:** interviews, workshops, observation (job shadowing), surveys, document analysis, prototyping, focus groups.
- **When to use which:** e.g., observation is great when users can't fully explain what they do.
- **Practice:** Pick the best technique for 3 scenarios (busy executive, whole department, undocumented legacy process).

### Lesson 5 — Stakeholder Analysis
- **What:** Identify *who* matters, their influence, and how to engage them.
- **Tools:** **Power/Interest grid** (manage closely / keep satisfied / keep informed / monitor) and **RACI** (Responsible, Accountable, Consulted, Informed).
- **Practice:** Build a mini power/interest grid for a payroll-upgrade project.

### Lesson 6 — Core BA Documents (Overview)
- **BRD** (Business Requirements Document) — the *why/what* at business level.
- **FRD / SRS** (Functional Requirements / Software Requirements Spec) — detailed system behavior.
- **User Story** — Agile lightweight format: *"As a &lt;role&gt;, I want &lt;goal&gt;, so that &lt;benefit&gt;."*
- **Practice:** Convert one MISA feature into a user story.

### Lesson 7 — Agile vs. Waterfall (and the BA's place)
- **Waterfall:** big upfront requirements, sequential phases. BA writes big docs (BRD/FRD).
- **Agile:** iterative, requirements evolve. BA writes user stories, refines a backlog, works with a Product Owner & team.
- **Practice:** List one pro and one con of each for an accounting-software project.

### Lesson 8 — Requirements Documentation & Traceability (intro)
- **What:** Keeping requirements clear, uniquely IDed, and traceable from business goal → feature → test.
- **Tool:** a simple **Requirements Traceability Matrix (RTM)**.
- **Practice:** Sketch a 3-row RTM linking a goal → requirement → test.

---

## ✅ Phase 1 deliverables (proof you learned it)
- A one-page "BA mindset" cheat sheet in your own words.
- A filled **stakeholder power/interest grid** for a sample project.
- One example of **each requirement type** for a feature.
- 3 user stories converted from real MISA features.

## 🧪 Self-check before moving to Phase 2
- Can I explain problem vs. solution to a friend in 60 seconds?
- Can I name the 4 requirement types and give an example of each?
- Can I pick an elicitation technique for a given situation and justify it?
- Do I know what a BRD, FRD, and user story are for?
